# OmniVoice + FastAPI + React --- Project Roadmap

## 1. Final Goal

Build and deploy a full Text-to-Speech (TTS) web application.

A user opens a React web interface, enters text, selects supported voice
options, clicks **Generate Speech**, and receives playable/downloadable
audio generated by the real **OmniVoice** model through a **FastAPI**
backend.

**Required stack** - **Model:** Official OmniVoice repository and
pretrained model - **Backend:** Python, FastAPI, Pydantic -
**Frontend:** React, HTML, CSS, JavaScript - **Version control:** Git
and GitHub connection - **Inference:** CPU-only for the initial
implementation - **Deployment:** Frontend and backend deployed after
local testing

**Core request flow**

``` text
User
  |
  v
React UI (HTML/CSS/JavaScript)
  |
  | HTTP request (JSON)
  v
FastAPI backend
  |
  v
OmniVoice service
  |
  v
Real OmniVoice model running on CPU
  |
  v
Generated WAV audio
  |
  v
FastAPI returns audio URL / file response
  |
  v
React audio player + download option
```

------------------------------------------------------------------------

## 2. Project Rules

1.  Start from a clean, documented setup and proceed one step at a time.
2.  Keep the model repository, backend, and frontend clearly separated.
3.  Use a separate Python virtual environment for the FastAPI backend.
    Do not reuse the model repository's `.venv`.
4.  Use CPU-only PyTorch for the initial version. Do not install
    CUDA-specific PyTorch unless the plan changes.
5.  Prove that OmniVoice can generate a WAV file in a standalone Python
    test before integrating it into FastAPI.
6.  Do not implement a mock TTS backend. The application workflow must
    call the real OmniVoice model. Use a standalone real-inference test
    before integrating the model into FastAPI.
7.  Use Git branches and commits so changes can be reviewed and
    reverted.
8.  Never commit secrets, `.env` files, virtual environments, generated
    audio, model weights, or large caches.
9.  Use only voice modes and request fields supported by the installed
    OmniVoice version. Validate against its current official
    repository/API.
10. CPU inference may be slow and may require substantial RAM. Measure
    latency and memory before choosing a deployment host.

## 7. Phase 3 --- Build the FastAPI Backend

**Goal:** Provide a stable HTTP API that can generate and serve speech.

Suggested initial endpoints:

  ---------------------------------------------------------------------
  Endpoint                           Purpose
  ---------------------------------- ----------------------------------
  `GET /health`                      Check whether the API process is
                                     responding

  `GET /health/model`                Report whether the model is
                                     loaded, without exposing secrets

  `POST /api/tts`                    Validate text and request speech
                                     generation

  `GET /api/audio/{filename}`        Retrieve generated audio safely
  ---------------------------------------------------------------------

### Backend responsibilities

-   Validate text length and supported voice options with Pydantic.
-   Keep model loading in `tts_service.py`, not directly in the route
    handler.
-   Load/cache the model once per worker process, rather than reloading
    for each request.
-   Run inference on CPU for the initial version.
-   Save generated WAV files under the configured output directory.
-   Return a response containing a generated audio URL or a file
    response.
-   Use safe generated filenames and prevent path traversal.
-   Return clear HTTP errors if model loading or generation fails.
-   Add CORS configuration for the local React development origin.
-   Keep model errors in server logs; return safe messages to the
    client.
-   Do not include mock mode in the application. The TTS service must
    call the real OmniVoice model.

### Backend `.env.example`

``` dotenv
TTS_DEVICE=cpu
OMNIVOICE_MODEL_ID=k2-fsa/OmniVoice
OUTPUT_DIR=outputs
FRONTEND_ORIGIN=http://localhost:5173
```

This is an example only. Keep the real local `.env` untracked. Configure
the service for real OmniVoice CPU inference; do not add a mock backend
setting.

**Exit criteria:** The API can accept text, call the real model, and
return a working audio result.

## 10. Phase 6 --- Deployment

**Deploy only after local real-model generation and end-to-end tests
work.**

### Backend deployment

Choose a host that supports: - The required Python version and native
dependencies. - Enough RAM for loading OmniVoice and running
inference. - Long-running CPU inference requests. - Persistent storage
if generated audio must remain available. - A way to configure
environment variables and logs.

Deployment tasks: 1. Pin tested Python dependencies. 2. Create a
production start command for FastAPI. 3. Configure model
caching/download behavior. 4. Configure allowed frontend origins in
CORS. 5. Store secrets and settings in the host configuration. 6. Add
request limits and sensible timeouts. 7. Test startup, model loading,
memory use, latency, and failure handling. 8. Decide whether generated
files should be temporary or stored persistently.

### Frontend deployment

1.  Set the production `VITE_API_BASE_URL` to the deployed backend URL.

2.  Build the React app:

    ``` powershell
    npm run build
    ```

3.  Deploy the generated `dist/` directory to a static hosting provider.

4.  Configure CORS on the backend for the deployed frontend domain.

5.  Test the complete deployed flow from browser to backend to generated
    audio.

### Deployment caution

CPU inference can be slow. Measure the generation time for short and
longer text before selecting a hosting plan. A successful local test
does not guarantee that a low-memory hosting plan will work.

Do not copy any `.venv`, `node_modules`, `.env`, generated WAV files, or
downloaded model cache into Docker images. Use `.dockerignore` files and
keep secrets outside the image.

### Backend container considerations

-   Use a Python base image compatible with the tested OmniVoice
    dependencies.
-   Install only the pinned, tested Python packages.
-   Start FastAPI using a production ASGI server command, for example
    `uvicorn app.main:app --host 0.0.0.0 --port 8000`.
-   Run inference on CPU (`TTS_DEVICE=cpu`) for the first deployment.
-   Do not assume the model cache is included in the image. Choose and
    test a model-download/cache strategy.
-   Ensure the server has enough RAM for model loading and inference.
-   Consider one worker initially: each separate worker may load its own
    model and multiply RAM use.
-   Mount persistent storage only if generated audio must remain
    available after container recreation.

### Frontend container considerations

-   Build the React app using the Node build stage.
-   Serve the static `dist/` output through a small web server such as
    Nginx.
-   Configure the production API URL correctly. A browser-side
    `localhost` URL refers to the user's own computer, not the deployed
    API server.
-   Set the backend CORS allowlist to the deployed frontend origin.

## 14.4 Local Docker Compose deployment

Use Docker Compose to run the FastAPI backend and React frontend
together. This project does not currently require a database or cache,
so do not add PostgreSQL or Redis unless a later requirement needs them.

Illustrative `deploy/compose.yaml`:

``` yaml
services:
  backend:
    image: ${DOCKER_USERNAME}/omnivoice-backend:${IMAGE_TAG:-latest}
    environment:
      TTS_BACKEND: real
      TTS_DEVICE: cpu
      OMNIVOICE_MODEL_ID: k2-fsa/OmniVoice
      OUTPUT_DIR: /app/outputs
      FRONTEND_ORIGIN: ${FRONTEND_ORIGIN:-http://localhost:8080}
    volumes:
      - audio_outputs:/app/outputs
      - model_cache:/root/.cache
    expose:
      - "8000"
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health', timeout=5)"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 180s

  frontend:
    image: ${DOCKER_USERNAME}/omnivoice-frontend:${IMAGE_TAG:-latest}
    ports:
      - "8080:80"
    depends_on:
      backend:
        condition: service_healthy
    restart: unless-stopped

volumes:
  audio_outputs:
  model_cache:
```

This is a template, not a ready-to-run configuration. The
backend/frontend image names, Dockerfiles, environment variable names,
model-loading behavior, and frontend API routing must match the actual
implementation before use. The health-check start period may need to be
longer because loading a speech model can take time.

If the React frontend uses a relative API path, configure the frontend
web server to proxy `/api/` requests to the `backend` Compose service.
Otherwise, configure a public backend URL and CORS explicitly. Do not
expose the backend port publicly unless required.

Example commands after the images and configuration are ready:

``` powershell
docker compose -f deploy/compose.yaml config
docker compose -f deploy/compose.yaml pull
docker compose -f deploy/compose.yaml up -d
docker compose -f deploy/compose.yaml ps
docker compose -f deploy/compose.yaml logs -f backend
```

For local testing, images can be built directly instead of pulled from
Docker Hub. Do not run this deployment stage until real model inference
works in the application.

## 14.6 Health checks and troubleshooting

FastAPI should expose at least:

-   `GET /health`: reports that the API process is responding.
-   `GET /health/model`: reports model readiness without revealing
    secrets.

Model readiness should reflect the actual application state; an HTTP
process being alive does not guarantee that OmniVoice has loaded
successfully. Consider a startup/loading state and a clear error state.

Useful commands:

``` powershell
docker compose ps
docker compose logs --tail=200 backend
docker compose logs --tail=200 frontend
docker stats
```

Check these conditions:

-   The backend starts and the health endpoint responds.
-   The model can load from the configured cache or model source.
-   A short text can be synthesized successfully.
-   The returned WAV is accessible to the frontend.
-   The container does not repeatedly restart or run out of memory.
-   CORS or reverse-proxy rules do not block frontend requests.

-   Model loading time and readiness.
-   CPU and RAM usage.
-   Container restarts and out-of-memory events.
-   Number of generation requests in progress.
-   Output generation failures.

Do not expose a Prometheus metrics endpoint publicly without appropriate
network restrictions. Avoid logging full user text or sensitive content
unless there is a clear need and suitable privacy controls.

### Initial alert ideas

-   API health check has failed for several consecutive checks.
-   Container is restarting repeatedly.
-   Memory usage is near the configured container limit.
-   Speech generation error rate increases.
-   Generation latency exceeds the agreed threshold.
-   Disk usage grows due to accumulated generated audio.

Thresholds should be set after measuring real CPU inference on the
target server. CPU utilization alone is not a reliable measure of
whether speech generation is healthy.

## 14.8 Security and reliability checklist

-   [ ] `.env`, tokens, credentials, and private configuration are
    excluded from Git.
-   [ ] Container images use tested dependency versions.
-   [ ] Images are scanned before production deployment.
-   [ ] Production uses versioned image tags.
-   [ ] API and frontend run with only required network exposure.
-   [ ] CORS allows only the intended frontend origins.
-   [ ] Audio output filenames and paths are validated.
-   [ ] Request text length and request timeouts are bounded.
-   [ ] Generated audio retention and cleanup are defined.
-   [ ] Model cache storage and permissions are configured.
-   [ ] Health checks distinguish API liveness from model readiness.
-   [ ] Logs do not expose secrets or unnecessary user content.
-   [ ] A rollback path to the previous known-good image is documented.

## 14.9 Deployment milestones

1.  **Local application works:** real OmniVoice generates speech through
    FastAPI, and React can play/download it.
2.  **Docker works locally:** backend and frontend images build and run
    with Compose.
3.  **Health checks work:** API readiness and frontend access are
    verified.
4.  **GitHub CI works:** pushes trigger tests and image builds.
5.  **Registry works:** versioned images are pushed securely.
6.  **Server deployment works:** Compose pulls and starts the selected
    images.
7.  **Monitoring works:** logs and resource metrics are visible.
8.  **Alerts and rollback work:** unhealthy service or failed release
    can be detected and recovered.

The deployment is complete when a new GitHub change can be tested, built
into versioned images, deployed to the server, checked for health,
monitored, and rolled back if needed.
